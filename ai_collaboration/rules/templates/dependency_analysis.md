# 变更风险评估规范

本文档定义了对历史代码进行修改时的风险评估流程和标准。

## 1. 风险评估流程

### 1.1 识别影响范围

在修改任何历史代码前，必须识别以下影响范围：

| 影响类型 | 说明 | 识别方法 |
|---------|------|---------|
| 直接依赖 | 注入该Service的其他Service | 搜索 `@Autowired` 或构造函数注入 |
| 间接依赖 | 通过Mapper或Controller调用的模块 | 分析调用链路 |
| 数据影响 | 涉及的数据库表和字段 | 分析Mapper XML和Entity |
| 接口影响 | 对外暴露的API接口 | 分析Controller层 |

### 1.2 风险等级判断

| 等级 | 触发条件 | 必要措施 |
|------|---------|---------|
| 🔴 极高 | 涉及OrderService/DistributionService/SkuService核心方法 | 架构评审 + 全量回归测试 |
| 🔴 高 | 涉及anpin-service/anpin-dao模块的核心类 | 详细设计评审 + 核心流程测试 |
| 🟠 中高 | 涉及anpin-common/anpin-auth公共模块 | 代码评审 + 相关模块测试 |
| 🟡 中 | 涉及anpin-erp/anpin-open-api业务模块 | 代码评审 + 模块测试 |
| 🟢 低 | 独立子模块或新增功能 | 代码评审 + 单元测试 |

## 2. 高风险模块清单

基于依赖分析报告，以下模块修改需特别谨慎：

### 2.1 核心枢纽模块

- **anpin-service**：核心业务服务层，被7个模块直接依赖
- **anpin-dao**：数据访问层，所有数据库操作的核心

### 2.2 高复杂度Service

| Service | 代码行数 | 风险点 |
|---------|---------|-------|
| DistributionService | 2859行 | 代码量最大，逻辑复杂 |
| OrderService | 2200+行 | 存在循环依赖风险 |
| SkuService | 1800+行 | 被依赖最多，20+个Service |

### 2.3 循环依赖关注点

以下模块间存在循环依赖，修改时需特别注意：

```
OrderService ↔ DistributionService
（修改任一方需评估对另一方的影响）
```

## 3. 变更检查清单

在进行代码修改前，请确认以下检查项：

- [ ] 是否涉及核心Service（Order/Distribution/Sku）
- [ ] 是否修改公共方法签名
- [ ] 是否涉及数据库表结构变更
- [ ] 是否影响对外API接口
- [ ] 是否需要数据迁移
- [ ] 是否有对应的测试覆盖

## 4. 风险缓解措施

### 4.1 极高风险变更

1. 必须提交详细设计方案评审
2. 进行架构层面评审
3. 编写全量回归测试用例
4. 在测试环境充分验证
5. 制定回滚方案

### 4.2 高风险变更

1. 编写详细设计文档
2. 进行代码评审
3. 编写核心流程测试用例
4. 在测试环境验证

### 4.3 中等风险变更

1. 进行代码评审
2. 编写相关模块测试用例
3. 常规测试流程
