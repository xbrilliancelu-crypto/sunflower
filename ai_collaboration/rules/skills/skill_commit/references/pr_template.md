# Pull Request 模板

## 1. PR 标题规范

### 1.1 格式

```
<type>(<scope>): <简短描述>
```

### 1.2 示例

| 类型 | 示例 |
|------|------|
| 新功能 | feat(collector): 新增采集器管理功能 |
| Bug修复 | fix(auth): 修复登录验证失败问题 |
| 重构 | refactor(alarm): 重构报警规则匹配逻辑 |
| 文档 | docs: 更新部署文档 |

## 3. PR 合并规则

### 3.1 合并条件

| 条件 | 要求 |
|------|------|
| 代码审查 | 至少1人批准 |
| CI构建 | 必须通过 |
| 单元测试 | 必须通过 |
| 冲突解决 | 无冲突 |

### 3.2 合并方式

| 方式 | 适用场景 | 说明 |
|------|----------|------|
| Squash and merge | 单功能PR | 压缩为一个commit |
| Merge commit | 多功能PR | 保留完整历史 |
| Rebase and merge | 保持线性历史 | 变基后合并 |

**推荐**：大多数情况使用 **Squash and merge**

## 4. PR 审查指南

### 4.1 审查者职责

1. **功能正确性**：变更是否符合需求
2. **代码质量**：代码是否清晰、规范
3. **架构合规**：是否符合分层架构
4. **安全风险**：是否存在安全隐患
5. **性能影响**：是否有性能问题

### 4.2 审查意见格式

```markdown
## 审查意见

### 必须修改
1. [问题描述]
   - 位置：文件名:行号
   - 建议：[修改建议]

### 建议修改
1. [优化建议]

### 提问
1. [需要澄清的问题]
```

### 4.3 审查结果

| 状态 | 含义 |
|------|------|
| Approve | 同意合并 |
| Request Changes | 需要修改后重新审查 |
| Comment | 仅评论，不阻塞合并 |

## 6. PR 注意事项

### 6.1 创建PR前

- [ ] 代码已提交到正确的分支
- [ ] Commit Message符合规范
- [ ] 已拉取最新代码并解决冲突
- [ ] 本地测试已通过

### 6.2 PR创建后

- [ ] 关注CI构建结果
- [ ] 及时响应审查意见
- [ ] 更新后通知审查者
- [ ] 合并后删除分支
